Benchmark: baseline/FightRec.lua (old) versus recorder/FightRec.lua v2 (new) -- 2026-10-23
Author of harness and this report: Claude Opus 5.5 (claude-opus-5-5). Harness: bench/bench.lua (+ bench/null_recorder.lua); tables rendered by bench/summarize.py.

SCOPE AND LIMITS (read first)
- Host/mock measurements only: Lua 5.4 bundled in lupa 2.8 (Python 3.13 venv in work/, git-ignored) on an
  AMD Ryzen 7 9800X3D, 64 GB, Windows 11, with uncontrolled desktop load. Engine objects, Osiris, Ext.Json (a
  pure-Lua encoder, far slower than the extender's C++ one) and the file system are fakes (tests/mock_se.lua).
  Nothing here is Script Extender time, frame time or a live hitch measurement; no performance budget is claimed.
  The user-reported 35--186 ms hitches are not comparable to these numbers.
- Workload: deterministic synthetic fight, event mix weighted from the retained fight04 counts, gaps 300--1400 ms
  with 25% zero-gap bursts, Tick every 100 ms of mock time, N=8 or 24 actors (4 party), damage events with nested
  Hit/Attack/Result objects. The same seeded event list is fed to every recorder in a trial. Synthetic events do
  not reproduce evolving combat state.
- Configs: null (control: same hooks, no work); baseline; v2_default; v2_lean (no turn/action/dirty/reconcile
  checkpoints); v2_full (defaults + MOVEMENT_ENABLED + CHECKSUM=fnv1a32).
- Statistics: per trial, p50/p99/max of single dispatch times; tables give the MEDIAN over trials of p50/p99
  (med_trial) and the MAXIMUM over all trials (max_all). One warmup per cell (discarded); 5 trials (3 at E=4000).
  Timer host.hrtime_ns (perf_counter_ns via lupa), pair overhead p50 0.1 us / p99 0.2 us (n=20000), not subtracted.
- Memory: whole-harness Lua heap delta after full GC mid-fight (mock world + workload + recorder); the null control
  is shown beside it. Allocation volume is whole-harness with the collector stopped.
- Reproduce: python tools/lua54.py bench/bench.lua [--quick] [--out FILE]; python bench/summarize.py FILE.
  Final run work/bench/full-010.json / full-run-010.txt (git-ignored); the tables below are its summarize.py output,
  pasted verbatim, including the source hashes it was bound to (recorder 5c3ddbf6..., the frozen committed file).

READING THE RESULTS
- Statistics: ev/tick p50 and p99 are medians over trials of per-trial percentiles; *_max_all is the single worst
  dispatch over all trials and is host-noise dominated -- in this run even the null control reached a 13.8 ms
  tick at N=8 E=4000, and maxima differ widely between full-008/009/010 for identical deterministic behaviour.
  No tail claim is made from max values; p99 is the steadier signal. Long-session/writer-only/host-disk rows are
  one trial per size (trend, not a distribution).
- Bytes requested: slopes ~2 (baseline) vs ~1 (v2), consistent with DESIGN 5 under fixed C, cadence and shapes.
  At E=500 v2 requests MORE (19.6--22.6 MB vs 16.0--16.9 MB); lower from E=1000; 15.70 GB vs 0.69 GB at E=16000.
- Memory (whole-harness heap; null control alongside): baseline grows with history (841 -> 6602 KB over
  E=2000 -> 16000); v2 stays at ~100--350 KB, dominated by the active part (<= C). Name/stat caches still grow with
  distinct identities/prototypes (fixed in this workload), so the general bound includes O(U). Whole-harness
  heap with a null control is not exact recorder accounting.
- Writer-only (identical pre-encoded lines, same timeline; service/pump time only, excluding admission and line
  creation; old = documented re-implementation of the baseline writer semantics, not the baseline code itself):
  new requests 2.3x / 8.7x / 34.7x fewer bytes and spends 1.7x / 11.3x / 57.9x less service time at
  E=1000 / 4000 / 16000; retained heap 20 / 80 / 207 KB vs 287 / 1161 / 4826 KB. The new writer's worst single
  service call (4.9 ms at E=16000) is a part seal plus host noise; bounded size is not a frame-time guarantee.
- End-to-end per-event host cost: v2_default p50 is above the baseline in every cell (e.g. 96 vs 73 us at N=8
  E=1000) because it does more per event; v2_lean is close. Tick p99 of v2_default is ABOVE the baseline up to
  E=2000 (deferred checkpoints) and below it at E=4000 and in long sessions (207 vs 3741 us at E=16000). Live cost
  depends on SE reflection and the C++ encoder (PROFILE=true exists for live measurement).
- Disk bytes: v2_lean +32% (envelope, Result copy), v2_default ~3.4x the baseline, dominated by dirty/reconcile/
  turn checkpoints in this workload (most gaps exceed DIRTY_QUIET_MS=400). Knobs exist; defaults not retuned on
  synthetic data.
- Allocation (whole harness, GC stopped): v2 allocates MORE at E<=1000; the baseline grows superlinearly and would
  cross later; not measured beyond E=1000.
- Host disk (real NTFS writes through Python; NOT SE I/O), 3 trials: tick p99 460 vs 550 us at E=1000 and 1432 vs
  698 us at E=4000 (baseline vs v2). Single-tick maxima: baseline 51 ms (E=1000) and 28 ms (E=4000); v2 111 ms
  (E=1000) and 571 ms (E=4000). Earlier runs showed 67--133 ms (v2) and 1.6--101 ms (baseline). Cause not
  determined by this harness. v2 creates many more files (one per ~256 KiB part plus a probe read per new part);
  new-file scanning by the OS is one plausible, unverified contributor. This is a live risk to measure
  (docs/LIVE-CHECKLIST.txt T-03), not a property established for SE.
- UI: v2 never has more than one deferred poll queued (baseline up to 6 at D=3000 ms); the visual-tree search
  algorithm is unchanged and its timings (n=7) are host noise.

Provisional decision criterion (DESIGN 7), offline only: no unexplained seq/accounting errors in tests; no
unbounded history/queue in v2 in these workloads; lower rewrite I/O from E=1000. Costs: more bytes on disk at
defaults, more host CPU per event, more allocation at small E, and unexplained large single-tick maxima on real
host disk writes. Live thresholds remain to be agreed and measured (docs/LIVE-CHECKLIST.txt T-01..T-03).
